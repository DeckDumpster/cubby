# Cubby — component design (LLD)

The low-level design for [[cubby-hld-2026-10-17]] (approved). It fixes the shapes an aeon needs:
crates, schema, protocols, budget math and deploy, and cuts the work into beads. Everything here
is in service of the HLD's intent; where the two disagree, the HLD wins.

## Intent

Make each HLD work-breakdown row buildable by one aeon without design decisions of its own, and
make the safety properties testable: nothing outside the allow-list reaches the child, the budget
cannot be gamed by quitting early or scrubbing, and a revoked device stops at once.

## Repository layout

```
cubby/
  Cargo.toml                  workspace; rust 1.94, edition 2024
  crates/
    cubby-core/               pure domain: budget math, policy resolution, ranker trait + v1 ranker
    cubby-db/                 rusqlite: schema, migrations (PRAGMA user_version), registry, queries
    cubby-yt/                 YouTube Data API v3 client with a quota meter; recorded-fixture mode
    cubby-server/             axum: parent API, child API, identity, play grants; serves the SPA
    cubby-worker/             metadata worker binary (policy expansion, refresh)
  web/                        SvelteKit 5 static SPA: routes /parent/** and /watch/**
  deploy/                     Quadlet units, litestream.yml, cloudflared notes, deploy.sh
  tests/e2e/                  Playwright specs + a fake IFrame player
```

The Access JWT verifier, tenant registry and Litestream config are **copied and adapted** from
pokedumpster, not depended on (HLD decision). `cubby-core` has no I/O, so the budget and ranker
properties are tested as pure functions.

## Identity

- **Parent:** a verified Cloudflare Access JWT (RS256 via JWKS; `aud`, `iss`, `exp`, `nbf`), the
  same checks as pokedumpster's `access.rs`. The email maps to the family. All `/api/parent/*`
  and `/parent/*` require it.
- **Child device pairing:**
  1. The parent calls `POST /api/parent/children/{id}/pairing`, which returns a 6-character code
     (no ambiguous letters) valid for 10 minutes, shown big on the parent screen.
  2. The device calls `POST /api/child/pair {code}`, which returns a 256-bit random token. Only
     its SHA-256 is stored, in `devices.token_hash`.
  3. Every child call carries `Authorization: Bearer <token>`. A revoked or unknown token gets 401,
     and the child UI shows "ask a grown-up to set this iPad up again".
- Cloudflare Access applies to `/parent` and `/api/parent`. `/watch` and `/api/child` use an
  Access **bypass** policy, protected by the device token instead; `/api/child/pair` is
  rate-limited (5 attempts a minute per IP, and codes are single-use).

## Data model (DDL sketch, one family file)

```sql
children(id TEXT PRIMARY KEY, name TEXT, avatar TEXT, tz TEXT NOT NULL)
devices(id TEXT PRIMARY KEY, child_id TEXT, token_hash BLOB UNIQUE, label TEXT,
        paired_at INT, last_seen INT, revoked_at INT)
pairing_codes(code TEXT PRIMARY KEY, child_id TEXT, expires_at INT, used_at INT)
allow_policies(id TEXT PRIMARY KEY, kind TEXT CHECK(kind IN('video','channel','playlist')),
        youtube_id TEXT, child_id TEXT NULL /* NULL = all children */, added_at INT,
        removed_at INT)
allowed_videos(youtube_id TEXT, child_id TEXT NULL, policy_id TEXT,
        state TEXT CHECK(state IN('auto-allowed','approved','blocked')), changed_at INT,
        PRIMARY KEY(youtube_id, child_id, policy_id))
videos(youtube_id TEXT PRIMARY KEY, title TEXT, channel_id TEXT, channel_title TEXT,
        tags TEXT /* json */, duration_s INT, thumb_path TEXT, made_for_kids INT,
        fetched_at INT, unavailable_at INT)
videos_fts USING fts5(title, channel_title, tags, content='videos')
budgets(child_id TEXT PRIMARY KEY, video_equivalents REAL, window_s INT, minutes_cap INT,
        cutoff_mid_play INT NOT NULL DEFAULT 0,
        daily_windows TEXT /* json [["07:00","19:00"]] in child tz */)
play_grants(id TEXT PRIMARY KEY, child_id TEXT, device_id TEXT, youtube_id TEXT,
        granted_at INT, last_beat_at INT, max_position_s REAL, watched_s REAL,
        charge REAL, ended_at INT, end_reason TEXT)
requests(id TEXT PRIMARY KEY, child_id TEXT, kind TEXT CHECK(kind IN('like','more-from-channel')),
        youtube_id TEXT, created_at INT, resolved_at INT, resolution TEXT)
review_queue(...)   -- phase 2, not in v1 beads
```

**Playable** for a child means there is at least one `allowed_videos` row for (video, child or
NULL) in state `auto-allowed` or `approved`, **no** `blocked` row for that video and child, the
video isn't `unavailable`, and the policy isn't removed. One SQL view, `playable(child_id,
youtube_id)`, is the only thing the child API, search and the ranker read. That view is the
allow-list invariant.

## Metadata worker (`cubby-worker`, a systemd timer every 15 min)

- **Video policy:** one `videos.list` (batched, 50 ids per call, 1 unit) creates or refreshes the
  `videos` row; then an `allowed_videos` row in state `approved` (the parent picked it).
- **Channel policy:** `channels.list?part=contentDetails` gives the uploads playlist; then
  `playlistItems.list` pages through it (1 unit per 50). New ids get `videos` rows and
  `allowed_videos` rows in state `auto-allowed`, origin the policy. Later runs only page until
  they reach a known id.
- **Playlist policy:** the same as a channel's uploads, from the playlist id.
- Videos that come back private or removed get `unavailable_at` set and drop out of `playable`.
- **Quota meter:** each call records its unit cost in a daily counter; the worker stops at 8,000
  units a day and reports it. Thumbnails download once to `thumbs/` and are served by the server.
- Phase 2's search budget (20 calls a day) is a separate counter under the same meter.

## Budget engine (`cubby-core::budget`, pure)

Inputs: the child's `budgets` row, the grants in the window `[now - window_s, now]`, the child's
time zone and `now`.

- **Charge of a finished or live grant:** `f = min(1, watched_s / duration_s)`. The charge is `0`
  if `watched_s < min(30, 0.1 * duration_s)` (a mis-tap is free), else `f`.
- **watched_s** is accumulated from heartbeats, never taken from the client. Each beat
  `{position_s}` adds `min(position_s - prev_position, wall_elapsed)` when the position moved
  forward by at most wall-clock elapsed plus 2 seconds of slack. Seeking forward is not credited
  as watched; seeking back re-counts nothing. That defeats scrubbing to the end and claiming it
  watched, and also scrubbing to 95% and quitting to save budget, because what's charged is time
  actually watched.
- **Remaining:**
  - `video_equivalents_left = budget.video_equivalents - Σ charge`;
  - `minutes_left = budget.minutes_cap - Σ watched_s / 60`.
- **May start a play** when both are above 0 and `now` (in the child's time zone) is inside a
  daily window. Refusal reasons: `out-of-videos`, `out-of-minutes`, `not-now` (with the next
  window start), `not-allowed`.
- **Mid-play cutoff (off by default):** a per-child setting `budgets.cutoff_mid_play` (default
  false, per Ryan, 2026-10-17). Off: a video she has started always plays to the end, and the
  budget gates only the next start. Heartbeats still run, because they measure watched time for
  the charge, and an overrun is still charged against the next window and shown in the parent
  history. On: when either remaining value reaches 0, the beat response says `stop`, the page
  destroys the player and shows the "all done for now" card, with a grace of up to 60 seconds
  unless the time window closed.

## Play protocol (child API)

| Call | Behaviour |
|---|---|
| `GET /api/child/home` | child profile, remaining budget, grid sections (continue, liked channels, new from allowed channels, all), each item from `playable` |
| `GET /api/child/search?q=` | FTS5 over `videos_fts` joined to `playable`; ranked by bm25, then the ranker |
| `POST /api/child/play {youtube_id}` | budget and playability check, then `{grant_id, remaining}` or `{refused: reason}` |
| `POST /api/child/grant/{id}/beat {position_s, state}` | every 10 seconds while playing, and on pause, end or close; returns `{remaining, stop}` (`stop` only when `cutoff_mid_play` is on) |
| `POST /api/child/grant/{id}/end {reason}` | closes the grant (`ended`, `left`, `stop`); a missed end times out after 60 seconds without a beat |
| `GET /api/child/next?after={youtube_id}` | ranker output (12 tiles) plus remaining budget, for the end card |
| `POST /api/child/request {kind, youtube_id}` | a like or more-from-channel request; idempotent per child, video and kind per day |

## Ranker (`cubby-core::rank`)

```rust
pub trait Ranker {
    fn rank(&self, child: &ChildCtx, current: Option<&VideoMeta>, candidates: &[VideoMeta]) -> Vec<VideoId>;
}
```

The server passes **only** rows from `playable`, and `rank_checked()` drops any id not in the
input set, so a buggy ranker cannot leak a video. The v1 score is a weighted sum:
- same channel (3);
- shared tags (1 each, up to 3);
- unwatched (2);
- liked channel (2);
- recency of the upload (0 to 1).

It then de-duplicates against the last 10 watched. Embedding similarity can replace it later
behind the same trait.

## Child web UI (`web/src/routes/watch`)

- **Grid:** large thumbnails, a title of up to 2 lines, the channel avatar, and a budget badge at
  the top ("3 videos left today" plus a visual meter). No infinite scroll: sections, with "more"
  buttons.
- **Search:** a big search box; results come only from `/api/child/search`.
- **Watch page:** the player is created only after a grant, through the IFrame API from
  `www.youtube-nocookie.com` with `autoplay=0`, `rel=0`, `playsinline=1`, `fs=1` and
  `iv_load_policy=3`. On `ENDED` it destroys the player and shows the end card: the ranker's tiles
  and the budget. On `PAUSED`, when the page runs inside the iPad shell (user agent contains
  `CubbyShell/`), it shows the pause card over the player. Like and "more from this channel"
  buttons sit below the player.
- No `<a>` in the child DOM points off-origin; an e2e test asserts it.

## Parent web UI (`web/src/routes/parent`)

- **Allow-list:** paste any YouTube URL (`watch?v=`, `youtu.be/`, `/@handle`, `/channel/`,
  `/playlist?list=`). It resolves to a policy, shows a card, and offers per-child scope; there's a
  remove button.
- **"Added by your policies":** a list of `auto-allowed` videos with their origin, filterable by
  channel, with block and approve buttons per video.
- **Children:** name, avatar, time zone, budget fields, devices (pair, revoke).
- **History:** grants per child with watched time, charge and end reason.
- **Requests inbox:** likes and more-from-channel requests, with one-click "allow channel",
  "allow N more" and dismiss.

  `thumbs/`.
- **Cloudflare:**

  gate suffices is open question 2.

## Test strategy

- **Unit and property** (`cubby-core`, fast, no I/O):
  - budget charge and watched-time accounting against scripted heartbeat sequences (scrub
    forward, seek back, pause, tab close);
  - window edges and time zones;
  - the ranker invariant (proptest).
- **DB:** the `playable` view truth table; migrations up from empty.
- **API:** axum integration tests against a temp family file; YouTube via recorded fixtures only.
- **E2E:** Playwright in containers with a **fake IFrame player** (same event API, controllable
  clock), covering the child happy path, refusal, the end card, the pause card under the
  `CubbyShell` user agent, and the parent flows above.
