# Cubby — a child-safe, allow-list-only YouTube frontend (HLD)

YouTube is built to keep a child watching: autoplay, recommendations, end screens and the
"more videos" overlay all pull toward the next video, and YouTube Kids still decides what is
suitable. Ryan wants the opposite: hand his daughter an iPad that plays only videos he has
approved, never chains to the next one, and stops when her budget is spent (per Ryan,
2026-10-17). Approved by Ryan 2026-10-17 after review in hunk (first drafted as "Curio").

## Intent

1. **The allow-list is the universe.** The child can play, search and be recommended only
   videos a parent has allowed (directly, or through an allowed channel or playlist). Search and
   "more like this" exist, but every result is inside the allow-list. There is no autoplay and no
   path from the child UI to youtube.com.
2. **Feels like YouTube.** A thumbnail grid, a watch page, a search box and familiar controls,
   so a child needs no explaining. Measured by: she can find, pick and play a video unassisted
   on the iPad.
3. **Limits the parent sets are enforced by the server**, not the client, as a budget weighted
   by how much of each video was watched (see "Budget"), plus a watch-time cap and optional
   time-of-day windows. A refused play says why in child-friendly words, and her remaining budget
   is always visible.
4. **The parent decides every write.** Likes and "subscribe" never touch YouTube; they become
   requests in the parent's inbox. There are no comments at all.
5. **Parent control plane** on the web: curate the list (plain CRUD of video, channel and
   playlist URLs), review every individually playable video with an auditable state, set
   budgets per child, see watch history, answer requests, and (phase 2) review a queue of
   videos that *would have been* suggested.
6. **The website runs first;** the iPad app comes later on Ryan's MacBook as a thin shell
   around the child site, so nothing about the iPad blocks the server work here.

## Scope

- A new repository `cubby` (Rust workspace and a SvelteKit 5 app), built and landed by Spira
  (repo label `cubby`, local-only, landing on `local/main`; not on GitHub yet).
- The server: allow-list with per-video review state, children and budgets, play-grant
  enforcement, YouTube metadata cache, in-allow-list search and recommendations, watch history,
  child requests, parent API, child API.
- The parent web UI and the child web UI (one SvelteKit app, two route trees).
- Deploy on `ubuntu-mini-0` at **cubby.gantt.pub**: rootless podman Quadlet, a Cloudflare
  Tunnel route and an Access app on the gantt.pub zone, Litestream backups to S3, and CI.
- Telemetry from the first landing (law-every-component-sends-otlp).

## Non-goals

- **The native iPad app.** Ryan builds it on his MacBook against the running site. This design
  only fixes the contract it needs (device pairing, the child site URL, navigation lockdown).
- **Downloading, re-hosting or proxying video.** Playback is YouTube's own embedded player.
  Re-hosting would break YouTube's terms and cost storage and transcoding; it would buy offline
  play and full control of the player chrome. Out: legal risk, not engineering cost.
- **A custom video player** (yt-dlp streams into AVPlayer). Same cost and risk as above.
- **Code shared with the dumpster sites.** Cubby copies their proven patterns (file-per-tenant
  SQLite, Access JWT verification, Litestream config, Quadlet units) as its own code, with no
  `dumpster-kit` dependency (per Ryan, 2026-10-17: "copy only, no code sharing"). A dependency
  would save maybe a bead of setup but couple two unrelated products' release cycles.
- **Multiple families or public sign-up.** The tenancy pattern allows a second family later as a
  registry row, but there's no sign-up or billing now. Sign-up is roughly 2-3 beads plus abuse
  handling; it buys nothing for one family.
- **Content classification or AI moderation.** The parent is the filter. A classifier would be
  several beads and still need the parent's veto; it buys triage speed for the phase-2 queue
  only. The queue keeps room for a score column so a classifier can be added later (per Ryan,
  2026-10-17).
- **Comments.** None, in any direction.
- **Ad blocking.** The player is a cross-origin iframe Cubby cannot modify, network blocking
  breaks playback, and YouTube's API terms forbid interfering with embedded ads.

## Background / recon

- **Patterns to copy** from Ryan's other sites ([[architecture-inputs-2026-10-12]],
  [[shared-platform-2026-10-12]]): Rust 1.99.1 and axum 0.8 with rusqlite; a SvelteKit 5 static
  SPA; file-per-tenant SQLite with ULID ids and a registry; identity from a verified Cloudflare
  Access JWT; Litestream directory mode; rootless podman Quadlet on `ubuntu-mini-0` behind a
  Cloudflare Tunnel.
- **YouTube embedding** is allowed through the IFrame Player API. `autoplay=0` is honoured.
  Since 2018 `rel=0` only limits end-of-video suggestions to the same channel; it cannot turn
  them off. The paused-state "More videos" strip on desktop embeds cannot be disabled either.
  `youtube-nocookie.com` (privacy-enhanced mode) avoids cookies until play. To verify in the
  LLD against current docs.
- **Ads.** Made-for-kids videos carry only contextual, non-personalized ads. YouTube Premium
  removes ads in embedded players when the viewer's browser is signed in, at the cost of a Google
  login inside the iPad web view.
- **YouTube Data API v3**: `videos.list`, `channels.list` and `playlistItems.list` cost 1 quota
  unit per call; `search.list` costs 100; the default quota is 10,000 units a day.
  `relatedToVideoId` was removed in 2023, so there is no API for "what YouTube would have
  recommended". To verify in the LLD.

## Design

### Components

1. **cubby-server** (Rust, axum). One process, two API surfaces:
   - `/api/parent/*`: behind Cloudflare Access (Ryan's identity).
   - `/api/child/*`: authenticated by a **device token** issued when a parent pairs a device to a
     child profile. A child cannot do Access SSO, so this is an explicit, named non-Access route,
     rate-limited and revocable by the parent.
2. **cubby-web** (SvelteKit 5 SPA). Two route trees:
   - `/parent`: allow-list CRUD, the "added by your policies" review list, children and budgets,
     watch history, the requests inbox, and later the phase-2 review queue.
   - `/watch` (child): a thumbnail grid, a search box, and the watch page with the embedded
     player, end card and budget display.
3. **Metadata worker.** It fetches and caches title, thumbnail, duration, channel, tags and the
   made-for-kids flag via Data API v3 (1-unit calls). It expands allowed channels and playlists
   into individual videos (see "Review state") and stays well inside quota. Thumbnails are cached
   so the child grid never calls YouTube until play.
4. **In-allow-list discovery.** Search runs locally over cached metadata of allowed videos.
   Recommendations come from a **ranker** behind one interface: given the child, the current
   video and the allow-list, return a ranked list of allowed video ids. v1 ranks by same channel,
   then shared tags, then unwatched, then liked. Cosine similarity over embeddings of title and
   metadata can replace it later without touching the invariant. **Invariant: every candidate is
   in the child's allow-list**, enforced at the interface, not trusted to the ranker.
5. **Store** (rusqlite, the copied tenancy pattern): one file per family holding children,
   devices, allow-list entries and per-video review state, budgets, play grants, watch history and
   requests.
6. **iPad shell (later, not built here)**: a SwiftUI app whose one WKWebView loads `/watch` with
   the device token. It refuses navigation outside the Cubby origin, covers the paused player,
   and relies on iOS Guided Access or Screen Time single-app mode so the iPad cannot leave it. It
   can optionally sign in to a YouTube Premium family account for ad-free playback (a parent
   setting, off by default).

### Review state: every playable video is auditable

Allowing a channel or playlist is a *policy*. The metadata worker expands it into one row per
video, each carrying an **origin** (`direct`, or `via channel X` / `via playlist Y`), a
**state** (`auto-allowed` by policy, `approved`, `blocked`) and timestamps. The parent sees an
"added by your policies" list and can block any single video that arrived through a channel,
without losing the channel. Only `auto-allowed` and `approved` videos are playable, searchable or
recommendable (per Ryan, 2026-10-17).

### Budget: weighted by what was actually watched

Per child, per rolling window Z:
- a **video budget** in video-equivalents: each play costs the **fraction watched** (0..1). A
  mis-tap is free: under 10% or 30 seconds, whichever is less. Quitting at 95% costs 0.95, so
  stopping just before the end buys nothing.
- a **watch-time cap** of M minutes.
- optional **time-of-day windows** (for example no watching after 7 PM).

Play stops at whichever limit runs out first. The fraction watched is computed by the server from
player progress heartbeats on the play grant, never trusted from a single final client report
(per Ryan, 2026-10-17: a combination of play time and quantity, weighted by fraction watched,
with the benefit of the doubt).

### The play path

1. The child taps a video. The child UI asks `POST /api/child/play {video_id}`.
2. The server checks that the video is playable for this child, that the budget and watch-time
   cap have room, and that the time window is open. It then records a **play grant** and returns
   it with her remaining budget. Otherwise it returns a reason, shown in child-friendly words.
3. Only with a grant does the watch page create the YouTube IFrame player: `autoplay=0`,
   `rel=0`, `playsinline`, the privacy-enhanced host. The page sends progress heartbeats on the
   grant.
4. **No chaining:** on `ENDED` the page tears the player down and shows Cubby's own end card: a
   grid of allowed suggestions from the ranker, plus her **remaining budget** ("2 videos left
   today" and a visual). Nothing plays until she taps, and each tap goes back through step 2.
5. **Pause:** on the iPad, Cubby's own pause card covers the player, so YouTube's "More videos"
   strip is not reachable (desktop browsers are not a supported child device).

### Child writes become parent requests

The child UI has a "like" heart and a "more from this channel" button. Neither touches YouTube,
since she has no YouTube account in Cubby. Each tap writes a **request** row (child, video or
channel, kind, time). The parent's requests inbox offers "allow this channel", or "allow more
videos from it" at video grain. Likes also feed the ranker and the parent's view of what she
enjoys.

### Phase 2: the "would have been recommended" queue

With no related-videos API, candidates come from legitimate sources: other uploads from the
channels she watched (1-unit `playlistItems`), and keyword search on watched titles and tags
(`search.list`, **at most 20 calls a day**, 2,000 units). They are queued with a thumbnail and a
reason ("same channel as X"), approved or rejected in batches. The queue's layout leaves room for
a classifier score. Scraping YouTube's watch-next list is rejected: it breaks their terms and
changes without notice.

### Telemetry (designed in, law-every-component-sends-otlp)

Plays granted and refused by reason; video-equivalents and minutes used per child per window;
time to first frame; requests created and resolved; metadata-worker quota used per day;
review-queue depth and age; device-token failures. All pushed as OTLP to VictoriaMetrics, with
one Grafana dashboard.

### Data model (high level)

`children(id, name, avatar)` · `devices(id, child_id, token_hash, paired_at, revoked_at)` ·
`allow_policies(id, kind: video|channel|playlist, youtube_id, child_scope, added_at)` ·
`allowed_videos(youtube_id, child_scope, origin_policy_id, state: auto-allowed|approved|blocked, changed_at)` ·
`videos(youtube_id, title, channel_id, tags, duration_s, thumb_path, made_for_kids, fetched_at)` ·
`budgets(child_id, video_equivalents, minutes_cap, daily_windows)` ·
`play_grants(id, child_id, device_id, youtube_id, granted_at, watched_s, fraction, ended_at)` ·
`requests(id, child_id, kind: like|more-from-channel, youtube_id, created_at, resolution)` ·
`review_queue(id, child_id, youtube_id, reason, score, state)` (phase 2).

## Test strategy

- Unit: budget arithmetic (fraction charging, free mis-tap, window edges, time cap), allow-list
  resolution (policy expansion, a blocked video inside an allowed channel), the ranker invariant
  (no candidate outside the allow-list, property-tested), token hashing and revocation.
- Integration: the axum API against a fixture tenant file; the metadata worker against a recorded
  Data API fixture (no live quota in CI).
- End-to-end (Playwright in containers): child grid, then search, then play, then the end card
  with budget; refusal when spent; no reachable youtube.com link in the child DOM; a parent
  allows a channel, a video from it appears for the child, the parent blocks that one video, and
  it disappears.
- No live YouTube in CI: the IFrame player is stubbed with a fake that emits the same events.

## Decisions

All per Ryan, 2026-10-17, in review:
- Name **Cubby**, served at **cubby.gantt.pub** on a separate domain. Putting gantt.pub on
  Cloudflare is part of row 1.
- Allow-list grain: video, channel and playlist, with every playable video individually auditable
  and blockable.
- Search and recommendations exist, but only inside the allow-list. The ranker is replaceable;
  the invariant is not.
- Budget weighted by fraction watched, plus a time cap, with mis-taps free.
- Pause card covers the player on the iPad only.
- Multiple children from day one.
- Phase-2 search capped at 20 calls a day.
- Child likes and subscribes become parent requests; no comments.
- No code shared with the dumpster sites: patterns copied, not depended on.
- Ads accepted in v1 (made-for-kids contextual ads). An optional Premium login in the iPad shell
  is a parent setting, off by default. No ad blocking.
- Embed YouTube's own player rather than re-host or re-stream video.
- Enforce on the server with play grants.
