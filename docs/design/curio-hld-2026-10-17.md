# Curio — a child-safe, allow-list-only YouTube frontend (HLD)

YouTube is built to keep a child watching: autoplay, recommendations, end screens and the
"more videos" overlay all pull toward the next video, and YouTube Kids still decides what is
suitable. Ryan wants the opposite: hand his daughter an iPad that plays only videos he has
approved, never chains to the next one, and stops after N videos in Z time (per Ryan,
2026-10-17). Curio is a working name.

## Intent

1. **Allow-list only.** The child can play a video only if a parent has approved it (or its
   channel or playlist, if the parent chooses that grain). There is no search box, no
   recommendation, no autoplay, and no path from the child UI to youtube.com.
2. **Feels like YouTube.** A thumbnail grid, a watch page and familiar controls, so a child
   needs no explaining. Measured by: she can pick and play a video unassisted on the iPad.
3. **Limits the parent sets are enforced by the server**, not the client: at most N plays per
   rolling window Z per child, plus optional time-of-day windows. A refused play says why in
   child-friendly words.
4. **Parent control plane** on the web: curate the list, set limits per child, see watch
   history, and (phase 2) review a queue of videos that *would have been* suggested, then
   approve or reject them offline.
5. **The website runs first;** the iPad app comes later on Ryan's MacBook and is a thin shell
   around the child site, so nothing about the iPad app blocks the server work here.

## Scope

- A new repository `curio` (Rust workspace and a SvelteKit 5 app), built in Spira.
- The server: allow-list, children and limits, play-grant enforcement, YouTube metadata cache,
  watch history, parent API, child API.
- The parent web UI and the child web UI (one SvelteKit app, two route trees).
- Deploy on `ubuntu-mini-0` like the dumpster sites: rootless podman Quadlet, Cloudflare
  Tunnel and Access, Litestream backups to S3, CI on ephemeral-ci (EC2).
- Telemetry from the first landing (law-every-component-sends-otlp).

## Non-goals

- **The native iPad app.** Ryan builds it on his MacBook against the running site. This design
  only fixes the contract it needs (device pairing, the child site URL, `lockdown` behaviours).
- **Downloading, re-hosting or proxying video.** Playback is YouTube's own embedded player.
  Re-hosting would break YouTube's terms and cost storage and transcoding; it would buy offline
  play and full control of the player chrome. Out: legal risk, not engineering cost.
- **A custom video player** (yt-dlp streams into AVPlayer). Same cost and risk as above.
- **Multiple families or public sign-up.** Built on the dumpster-kit tenancy kernel, so a second
  family is a registry row later, but no sign-up or billing now. Building sign-up is roughly
  2-3 beads plus abuse handling; it buys nothing for one family.
- **Content classification or AI moderation.** The parent is the filter. An automated
  classifier would be several beads and still need the parent's veto; it buys triage speed for
  the phase-2 queue only, so it is a phase-2 option at most.
- **Comments, likes, subscriptions, sharing.** None reach the child.

## Background / recon

- **Stack Ryan uses elsewhere** ([[architecture-inputs-2026-10-12]], [[shared-platform-2026-10-12]]):
  Rust 1.94 and axum 0.8 with rusqlite, a SvelteKit 5 static SPA, `dumpster-kit` crates for
  tenancy (file-per-tenant SQLite, ULID ids, registry), identity (a verified Cloudflare Access
  JWT), Litestream directory mode, deploy libs and `ui/` tokens; rootless podman Quadlet on
  `ubuntu-mini-0` behind one Cloudflare Tunnel; CI on EC2 through ephemeral-ci.
- **YouTube embedding** is allowed through the IFrame Player API. `autoplay=0` is honoured.
  Since 2018 `rel=0` only limits end-of-video suggestions to the same channel; it cannot turn
  them off. The paused-state "More videos" strip on desktop embeds cannot be disabled either.
  `youtube-nocookie.com` (privacy-enhanced mode) avoids cookies until play. To verify in the
  LLD against current docs.
- **YouTube Data API v3**: `videos.list`, `channels.list` and `playlistItems.list` cost 1 quota
  unit per call; `search.list` costs 100; the default quota is 10,000 units a day.
  `relatedToVideoId` was removed in 2023, so there is no API for "what YouTube would have
  recommended". To verify in the LLD.

## Design

### Components

1. **curio-server** (Rust, axum). One process, two API surfaces:
   - `/api/parent/*`: behind Cloudflare Access (Ryan's identity, as the dumpster sites).
   - `/api/child/*`: authenticated by a **device token** issued when a parent pairs a device to
     a child profile. A child cannot do Access SSO, so this path is an explicit, named non-Access
     route (dumpster N6), rate-limited and revocable by the parent.
2. **curio-web** (SvelteKit 5 SPA). Two route trees:
   - `/parent`: allow-list curation (paste a URL or ID, or approve a whole channel or playlist),
     children and limits, watch history, and later the review queue.
   - `/watch` (child): a thumbnail grid of allowed videos, plus a watch page with the embedded
     player.
3. **Metadata worker.** It fetches and caches title, thumbnail, duration, channel and
   made-for-kids flag via Data API v3 (1-unit calls), refreshes slowly, and stays well inside
   quota. Thumbnails are cached so the child grid never calls YouTube until play.
4. **Store** (rusqlite, kit tenancy): one tenant file per family holding children, devices,
   allow-list entries, limit policies, play grants and watch history; registry and Litestream
   from the kit.
5. **iPad shell (later, not built here)**: a SwiftUI app whose one WKWebView loads `/watch`
   with the device token, plus iOS Guided Access or Screen Time single-app mode so the iPad
   cannot leave it.

### The play path: where safety is enforced

1. The child taps a video. The child UI asks `POST /api/child/play {video_id}`.
2. The server checks three things: the video is on this child's allow-list, the limit (N plays
   per rolling Z) has room, and the time window is open. It then records a **play grant** and
   returns it. Otherwise it returns a refusal reason, which the UI shows in child-friendly
   words.
3. Only with a grant does the watch page create the YouTube IFrame player: `autoplay=0`,
   `rel=0`, `modestbranding`, `playsinline`, the privacy-enhanced host.
4. **No chaining:** on the player's `ENDED` event the page tears the player down and shows
   Curio's own "all done" card back to the grid. YouTube's end screen and its suggestions are
   never on screen long enough to tap.
5. **Paused state:** the "More videos" strip appears on pause. On pause the page shows Curio's
   own pause card over the player, so the strip is not reachable. Whether a covering overlay is
   acceptable under YouTube's terms is open question 3.
6. All outbound links from the player (YouTube logo, title) are neutralised by the iPad shell,
   which refuses navigation outside the Curio origin. On a desktop browser this cannot be fully
   prevented; the iPad is the supported child device.

### Phase 2: the "would have been recommended" queue

With no related-videos API, candidates come from sources Curio can read legitimately:
- other uploads from the channels of videos she watched (1-unit `playlistItems`);
- keyword search on the watched video's title or tags (100-unit `search.list`, budgeted per
  day).

They are queued for the parent with a thumbnail and a reason ("same channel as X"), approved
or rejected in batches. Scraping YouTube's own watch-next list is rejected: it breaks their
terms and changes without notice.

### Telemetry (designed in, law-every-component-sends-otlp)

Plays granted and refused, by reason; plays per child per window; time to first frame;
metadata-worker API quota used per day; review-queue depth and age; device-token failures.
All pushed as OTLP to VictoriaMetrics, with one Grafana dashboard.

### Data model (high level)

`children(id, name, avatar)` · `devices(id, child_id, token_hash, paired_at, revoked_at)` ·
`allow_entries(id, kind: video|channel|playlist, youtube_id, child_scope, added_by, added_at)` ·
`videos(youtube_id, title, channel_id, duration_s, thumb_path, made_for_kids, fetched_at)` ·
`limit_policies(child_id, max_plays, window_s, daily_windows)` ·
`play_grants(id, child_id, device_id, youtube_id, granted_at, ended_at)` ·
`review_queue(id, child_id, youtube_id, reason, state)` (phase 2).

## Test strategy

- Unit: limit arithmetic (rolling windows, edges), allow-list matching (video vs channel vs
  playlist grain), token hashing and revocation.
- Integration: the axum API against a fixture tenant file; the metadata worker against a
  recorded Data API fixture (no live quota in CI).
- End-to-end (Playwright in containers, as poke and star do): child grid, then play, then the
  ENDED card; refusal at N+1; no reachable youtube.com link in the child DOM; parent adds a
  video and it appears for the child.
- No live YouTube in CI: the IFrame player is stubbed with a fake that emits the same events.

## Open questions

1. **Name and hostname.** Default: `curio`, served at `curio.dumpster.cards` (it fits the
   existing Tunnel and Access setup). Or a separate domain?
2. **Allow-list grain.** Default: video, channel *and* playlist, so approving a trusted channel
   is one click, and the child sees new uploads from it automatically. Or video-only, maximally
   strict?
3. **Pause overlay versus YouTube's terms.** Covering the paused player hides the "More videos"
   strip but may count as interfering with the player. Default: cover it on the iPad only, where
   it matters, and accept the risk for a private, single-family deployment. The alternative is to
   live with the strip.
4. **Limit semantics.** Is a "play" a video started, or one watched past a threshold (for
   example 30 seconds, so a mis-tap isn't charged)? Default: a play counts after 30 seconds of
   watching.
5. **Multiple children from day one?** Default: yes. Profiles are cheap, and the device decides
   whose list it shows.
6. **Phase-2 search budget.** Default: at most 20 `search.list` calls a day (2,000 units),
   leaving most of the 10k quota for metadata.

## Decisions

- Embed YouTube's own player rather than re-host or re-stream video: it is legal and cheap, and
  it does the most important thing (no autoplay, no chaining) given end-card control.
- Enforce on the server with play grants: a client-side limit is trivially bypassed, and the
  iPad shell plus Guided Access closes the remaining escape routes.
- Reuse dumpster-kit and the dumpster deploy stack: everything except the YouTube parts already
  exists and is operated daily.
